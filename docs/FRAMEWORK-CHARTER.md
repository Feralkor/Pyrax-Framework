# Pyrax Framework — Charter

## Purpose

Pyrax Framework standardizes the reusable engineering method used to create operational intelligence products across logistics, transportation, manufacturing, maintenance, strategy and adjacent domains.

The framework exists to reduce repeated architectural work and concentrate new-product effort on domain-specific semantics, integrations, policies and user experience.

## Product equation

`Framework Core + Domain Pack + Integrations + Decision Policies + Operational UX = Solution`

## Scope

The framework defines:

- discovery method;
- source and semantic mapping;
- data contracts;
- operational state model;
- quality and reconciliation;
- evidence and lineage;
- signal and anticipation patterns;
- decision-support contracts;
- confidence and abstention;
- operational memory and outcomes;
- QA and Golden Cases;
- domain-pack structure;
- MCP/agent behavior;
- reusable templates.

## Out of scope

The framework does not prescribe:

- one database technology;
- one frontend stack;
- one cloud vendor;
- one LLM provider;
- one industry ontology;
- autonomous operational actions by default;
- machine learning where deterministic methods are sufficient.

## Reference products

The framework is distilled from recurring patterns used in:

- Inteligência Operacional — warehouse intelligence, D+1, replenishment, productivity and operational evidence;
- Route Engineer — fleet/transportation intelligence, HOS, ETA, fuel, safety, maintenance and route anticipation;
- NeuroGear — industrial/OEE and equipment-oriented operational intelligence.

These products are references, not dependencies.

## Core engines

### Truth Engine
Reconstructs what is known and certifies how it is known.

### Anticipation Engine
Detects risk, pressure, deviation, emerging constraints and opportunities.

### Decision Engine
Produces constrained, explainable and evidence-backed decision support.

### Operational Memory
Records observation, decision, action and outcome so the system can improve responsibly.

## Success criterion

A new solution should spend less effort reinventing architecture and more effort validating its domain, sources, semantics and decision logic.
